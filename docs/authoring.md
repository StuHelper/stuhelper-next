# 文档写作与维护

沟通与技术文档的语言要求见仓库根目录的 [AGENTS.md](https://github.com/StuHelper/stuhelper-next/blob/develop/AGENTS.md)。写作或审阅长期维护的文档前，加载相关写作技能。文档先说明具体行为，再解释必要的原因和限制。保留准确的专业术语，并在首次出现时解释可能影响理解的概念。

项目负责人于 2026-10-23 指定采用 [project-docs-starter 文档架构](https://github.com/lihaotong0712/project-docs-starter/tree/1c4c6bb1bd401b803ea986b404932926cfc95eb0)。本项目沿用文档分类、主题索引、模板、元信息和状态管理方式，并按实际需要编写正文与检查工具。依赖版本和检查命令见[仓库检查指南](guide/repository-checks.md)。

## 内容归属

| 分类 | 至少回答 | 本项目例子 |
| --- | --- | --- |
| design | 要解决什么问题，机制是什么，为什么这样选择 | 模块边界、开课模型、SSO 更新机制 |
| spec | 哪些条件下出现什么可观察结果，怎样验收 | 原账号登录、模块关闭、资料下架 |
| development | 哪些事实已核实，当前任务是什么，实际验证到哪里 | 重写路线、SSO 迁移、文档重组 |
| guide | 前提是什么，执行哪些已有操作，如何检查结果 | 本地检查、CI 切换、候选解析 |
| adr | 哪个重要选择已作出，依据与后果是什么 | 官方镜像、BJ1 Registry 的 runner 选择 |

每条完整规则只维护一处。设计链接到行为规格，计划链接到验收场景，指南链接到已有脚本。其他文档通过链接引用数据保留清单、验收表和操作步骤。机器可读定义直接链接到源文件，并说明文件包含的内容。

## 写作与导航

按主题在分类内使用 `kebab-case.md` 文件名。类别入口维护主题索引，总入口只维护分类导航；规模确实需要时再建立主题子目录。新增文档从该分类 `TEMPLATE.md` 开始，删去不适用章节，不预建空文档集。

需求、调研、原型、设计和规格可以逐步完善。定义功能时先写清规则，并给出正常、边界和失败场景，再安排实现与验证。小修正可只在 PR 记录。开发记录应包含继续工作所需的文件、版本、任务和环境信息。

中文一段一行，使用软换行阅读；代码、表格和图表保留其结构。写清具体对象、条件、动作和结果，区分要求、建议、观察和推断。使用可定位来源，保留未知项与例外，不把来源版本、当前部署和目标版本混写。

移动文档时修复所有出入链接与 MkDocs 导航，旧文本由 Git 历史保留。文档站只打包 `docs/`；仓库源码、候选记录和工作流用 GitHub 源文件链接，避免生成站点出现指向站外本地路径的坏链接。

## 元信息与状态

`docs/` 中每份 Markdown 使用以下字段，分类直属文件的 `type` 与目录同名；总入口和本维护约定为 `index`：

```yaml
---
type: design
status: InReview
updated: 2026-10-23
---
```

`updated` 记录实质修改日期，不表示重新验证。模板的日期可使用 `YYYY-MM-DD`；主题文档使用真实日期。

| 状态 | 含义 |
| --- | --- |
| Draft | 仍在起草，问题和范围可不完整 |
| InReview | 已形成可审阅的版本，重要选择仍待确认 |
| Accepted | 文档所述方案已确认，实施与验证进度见对应开发记录 |
| Rejected | 曾讨论但未被采纳，有追溯需要时保留 |
| Deprecated | 已不建议继续采用，写清支持范围与退出条件 |
| Superseded | 已有替代文档，保留替代范围和双向链接 |
| Archived | 结束维护，仅供历史查阅，提供当前入口或说明无后续项 |

确认依据可以是已有讨论、Issue 或 PR。已获授权的内容直接沿用，新增产品选择先征询用户。尚未确定的方案保持 `InReview`，问题汇总到[业务确认结果与延期事项](development/business-decisions.md)。

开发记录在正文使用“待开始、进行中、已完成、已取消”表示工作进度，任务勾选与实际证据对应。文档状态、工作进度和验证结果分别记录。测试数据验证、生产验收和发布结果应注明各自环境与范围。

## 变更与检查

行为改变更新 spec，机制改变更新 design，操作改变更新 guide，工作结果更新 development；只有需独立追溯的重要取舍才新增 ADR。被撤销的提案应同步清理专属代码、配置、测试和引用；已共享历史与无关改动按仓库规则保留。

提交前执行[检查指南](guide/repository-checks.md)中的格式、元信息、本地链接/锚点、工作流和文档站构建检查。检查器通过后仍需复核技术结论、数据边界和操作前提。未执行的生产动作、真实账号验证和平台真机验收在开发记录中明确写出。
