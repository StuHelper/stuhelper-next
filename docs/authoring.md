# 文档写作与维护

## 维护目标

文档保持可直接使用的当前状态。代码、接口、产品规则或操作方式变化时，在同一项工作中更新对应主题，删除过时段落并合并重复说明。Git 历史、PR 和 CI 保存变更过程与运行详情。

工程与语言要求见仓库根目录的 [AGENTS.md](https://github.com/StuHelper/stuhelper-next/blob/develop/AGENTS.md)。正文先说明行为、对象和条件，再解释必要的原因。使用清晰、具体的中文与准确的专业术语。

## 内容归属

| 分类 | 维护内容 |
| --- | --- |
| design | 机制、结构与当前选择的理由 |
| spec | 可观察行为、边界条件与验收场景 |
| development | 当前实施范围、完成条件与剩余工作 |
| guide | 当前工具的前提、命令、结果与故障处理 |
| adr | 当前重要决策、适用边界与取舍 |

完整规则集中在一个主题中，其他文档链接到该主题。机器可读定义和生成文件按各自检查流程保持一致。开发记录直接更新当前状态；精确源码组合、契约来源和锁文件承担可复现输入的职责。

## 写作与导航

主题使用 `kebab-case.md` 文件名。新文档从分类模板开始，保留需要的章节。类别入口用表格列出全部主题，总入口维护分类导航。新增、移动和删除主题时，同步修改入口、引用与 MkDocs 导航。

中文一段一行，使用软换行阅读。并列事项较多时拆成列表或表格。正文直接陈述当前规则，历史叙述仅在理解当前选择确有需要时使用。

文档站打包 `docs/`。站内文档互链使用相对路径；指向根目录源码、工作流或跨仓文件时使用 GitHub 地址。同仓源码链接会映射到本地检查。当前维护入口可使用维护分支，证据引用固定源码提交。

## 元信息与状态

每份 Markdown 使用 `type`、`status`、`updated`。分类直属主题的 `type` 与目录相同，总入口和本约定使用 `index`。`updated` 表示实质修改日期。模板日期使用 `YYYY-MM-DD`。

| 状态 | 含义 |
| --- | --- |
| Draft | 内容仍在起草 |
| InReview | 重要选择待确认 |
| Accepted | 本文范围的规则已确认 |
| Rejected | 当前提案未采纳 |
| Deprecated | 当前维护建议使用替代方案 |
| Superseded | 主题已由指定文档替代 |
| Archived | 主题结束维护 |

文档状态、实施进度和验证范围分别表达。已确认规则直接维护为 Accepted，功能进度由对应 development 主题说明。

## 检查

按[检查指南](guide/repository-checks.md)执行格式、元信息、链接、导航、术语与严格构建检查。业务场景与测试通过编号关联，当前实现范围及相关结果集中在[框架状态](development/framework-bootstrap.md)。
