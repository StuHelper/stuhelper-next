## 阶段提案与完成条件

下表是早期实施顺序提案，不缩减[已确认业务范围](../design/business-scope.md)。本轮新增确认的可选实名、课表、QQ、开放平台、存储贡献及货币体系需要在排期时明确阶段，不能自动归为不做或全部挤入首期。

| 阶段 | 成果 | 完成条件 |
| --- | --- | --- |
| P0：工程初始化 | 公共仓库、五类文档、模块图、基础 CI、官方候选解析 | 精确提交检查通过；托管/自建 runner 实际执行分别记录 |
| P1：独立 SSO | 生产现状清点、官方 v4 固定候选、完整数据备份/恢复、AI/Store/旧站兼容 | 通过全量消费者矩阵；正式维护窗口切换；单一独立更新入口；没有业务启动依赖 |
| P2：最小业务闭环 | identity/access/campus/catalog/reviews，Web + 管理端 | 登录 → 查课程 → 看开课/教师 → 写评价 → 审核 → 展示；权限和旧数据迁移有测试 |
| P3：资料与互动 | media/resources，原生小程序/Android 首批客户端 | 资料上传、来源声明、访问权益和下架申请，以及互动/通知流程；货币解锁按确认规则验收 |
| P4：其余原生端 | iOS、HarmonyOS；端间设计与登录一致性 | 原生编译、真机验收、签名/发布门禁分别通过 |
| P5：按需求演进 | 个性化 feed、私信、实时功能、模块服务拆分 | 有实际产品与容量依据，隐私/审核/故障隔离契约通过 |

P1 的具体调查、演练和切换任务由[SSO 工作记录](sso-migration.md)维护，避免在本计划重复列清单。后续阶段按可独立验证的业务能力拆任务，引用对应规格场景。

## 旧业务数据迁移方案

各域分别建旧 ID → 新 ID 映射与导入证据；先只读导入和差异对账，再按域明确切换写入权威。账号始终复用 SSO subject；课程同名、教师同名、邮箱相同均不足以合并。历史评分、可见性、审核与学生资格来源需要保留，不只迁移“当前页面可见”的行。

避免让旧新系统长期同时修改同一业务事实。必要的并行阶段只读对照，通过路由按域切换；双写只有在定义持久重试、差异修复和退出条件后才考虑。API 兼容层有明确移除条件，不能变成永久跨库耦合。

## 待确认与验证限制

小程序首期暂按微信设计；社交首期范围、评价匿名/具体评分维度/编辑规则、客户端优先级与最低系统版本仍需收敛。评课学生资格、手机号门槛及五级展示已确认，不再列为未决。其余业务问题在各规格维护，会员套餐和实际奖励/价格配置仍需单独确定。移动端签名和商店账号、HarmonyOS SDK 环境、ArkTS 生成器能力尚未验证。

SSO 的旧会话处理与维护窗口由迁移任务解决；容量、SLO、RPO/RTO 根据实际业务和基准测试确定。当前没有业务 API、客户端构建、Docker build 或 Registry 网络性能验收结果。
