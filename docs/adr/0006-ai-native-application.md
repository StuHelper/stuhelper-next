# 0006：采用 AI native 应用形态

## 背景与决定因素

学生的常见问题往往跨越多个页面，例如“明天上什么课”“周三下午有没有空”“这门课哪位老师风评最好”。逐页查找需要用户自己组合课表、日程和评价。

项目尚未开放生产环境，因此现在调整产品形态不需要迁移线上用户。catalog、reviews、resources 等模块已有候选实现，调整时要保留已验证的业务规则和数据边界。

## 决策与确认依据

- Web 首页以对话为中心，支持文字、语音输入和实时通话，并默认展示今日课程和近期 DDL。
- Agent 与 Web 同为正式使用方。每个模块声明自己的工具，由 Service 继续执行全部业务规则。
- 新增 assistant 模块负责对话和 Agent 运行，新增 planner 模块负责个人日程、DDL 和空闲时间。
- Agent 读写本人数据由用户自主授权。用户授权不能扩大账号原有权限，也不能开放他人数据。
- 首期对外 MCP 只面向用户本人的客户端，并且只提供只读工具。第三方应用继续走[开放平台](../spec/open-platform.md)审核。
- Agent 和 MCP 遵守与页面相同的内容准入。首期所有写操作都由用户确认。

项目负责人于 2026-11-01 确认按此方案调整。模型的合规和数据出境由项目负责人选型时负责，本决策只要求模型可以通过网关替换。

## 备选与取舍

| 候选 | 取舍 |
| --- | --- |
| 在现有页面外增加聊天助手 | 改动最少，但工具和规则容易与业务模块脱节，因此未采用 |
| 模型直接决定业务结果 | 开发快，但模型出错时可能越权或算错，因此资格、权限和时间计算都由代码完成 |
| 只保留对话，移除传统页面 | 界面单一，但模型故障时无法查课表，看周课表也更慢，因此保留结果页面 |
| 按固定等级禁止个人数据外发 | 规则简单，但用户无法自行决定，已由自主授权取代 |

## 后果与验证

新增模块和新业务接口都要声明 Agent 工具。已实现模块需要补工具声明，catalog 还要把课表自由文本扩展为可计算的时间。

Agent 增加了模型费用、提示注入和回答质量风险，需要额度控制、确认流程和评测集。验收场景见 [Agent 助手规格](../spec/agent-assistant.md)和[个人日程规格](../spec/personal-planner.md)，进度见[实施记录](../development/ai-native.md)。

## 关联与替代

机制见 [AI native 架构](../design/ai-native-architecture.md)。本决策不替代已有 ADR，现有独立 AI 应用保持原有用途。
