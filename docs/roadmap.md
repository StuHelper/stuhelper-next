# 实施路线与验收

先把身份兼容这条关键路径完成，再扩展业务。无需等所有 App 写完才让新站上线；SSO 独立化也无需等待业务重写。

| 阶段 | 成果 | 完成条件 |
| --- | --- | --- |
| P0：本次初始化 | 公共仓库、架构提案、模块图、基础 CI、官方候选解析 | 精确提交检查通过；托管/自建 runner 实际执行分别记录 |
| P1：独立 SSO | 生产现状清点、官方 v4 固定候选、完整数据备份/恢复、AI/Store/旧站兼容 | 通过全量消费者矩阵；正式维护窗口切换；单一独立更新入口；没有业务启动依赖 |
| P2：最小业务闭环 | identity/access/campus/catalog/reviews，Web + 管理端 | 登录 → 查课程 → 看开课/教师 → 写评价 → 审核 → 展示；权限和旧数据迁移有测试 |
| P3：资料与互动 | media/resources，原生小程序/Android 首批客户端 | 资料上传/扫描/授权下载，发布/关注/评论/举报/通知完整流程 |
| P4：其余原生端 | iOS、HarmonyOS；端间设计与登录一致性 | 原生编译、真机验收、签名/发布门禁分别通过 |
| P5：按需求演进 | 个性化 feed、私信、实时功能、模块服务拆分 | 有实际产品与容量依据，隐私/审核/故障隔离契约通过 |

## P1 的交付拆分

1. 无生产修改的事实清单和差异矩阵；明确上游官方替代方案以及尚不支持项。
2. 独立运维包：不依赖业务主站；数据/配置由受控 secret backend 注入；本地 Compose 或部署系统可运行同一锁定镜像。
3. 合成消费者测试和生产快照隔离演练；先处理 AI/Store 的实际不兼容，再重新跑原失败用例。
4. 生产维护计划：精确候选、数据范围、窗口、恢复边界、负责人；确认具体停机选择后实施。
5. 全量验收与旧控制面退出。删除旧备份/镜像不包含在切换动作中。

## 旧业务数据的迁移原则

各域分别建旧 ID → 新 ID 映射与导入证据；先只读导入和差异对账，再按域明确切换写入权威。账号始终复用 SSO subject；课程同名、教师同名、邮箱相同均不足以合并。历史评分、可见性、审核与学生资格来源需要保留，不只迁移“当前页面可见”的行。

避免让旧新系统长期同时修改同一业务事实。必要的并行阶段只读对照，通过路由按域切换；双写只有在定义持久重试、差异修复和退出条件后才考虑。API 兼容层有明确移除条件，不能变成永久跨库耦合。

## 需要在实施前收敛的产品决定

- 小程序第一目标按微信处理；其他平台后续单独规划。
- 社交第一期按动态/关注/评论/收藏/通知处理，私信和群聊后置。
- 课程与教师评价的实名/匿名展示、学生资格门槛、评分维度和编辑政策。
- 各端交付优先级、最低系统版本，以及 iOS/HarmonyOS 发布账号与签名环境。
- SSO 首次迁移的实际停机窗口和已证实不兼容旧会话的处理方式。

这些待定项不妨碍本次建仓与设计；涉及生产数据、可见性和登录连续性的项须在对应实施阶段明确。
